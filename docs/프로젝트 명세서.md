## 1. 문제 정의

> “아 이 날에 내가 뭐했더라...?”
”즐거웠던 추억 사진을 다시 찾아 보고 싶은데... 어디있지...?”
> 
- 사진은 많이 찍는데, 원하는 사진을 다시 찾아보기가 힘듦.
    - 아무리 앨범 단위로 정리해도, **과거의 특정 순간**과 관련된 사진을 빠르게 찾기 어려움.
    - ex. 옛날에 먹은 개쩌는 케이크 사진을 친구에게 보여주고 싶은데, 
    이 사건이 언제 발생했는지 알지 못하면 찾기 힘들다…
- 우리는 보통 일기를 쓰지 않는다. 왜? 쓰는 것이 번거롭고 오래 걸리니까.
    - 그래서 과거에 특정 시점에서 내가 무엇을 했는지 기억이 잘 안 남.
    - 간단하게 나열식으로라도 하루를 텍스트로 정리하면 추후에 복기하기 쉬움.
- 사진 앱은 날짜별/앨범별 정리가 가능하지만, 그날의 이야기(장소 이동, 주요 이벤트, 사진 근거) 로 회고/검색하기 어려움.

→ 사용자 사진 및 위치 기반으로 자동으로 간단한 일기를 매일 생성하고, RAG 기반 검색 기능을 통해 사진과 일기를 쉽게 찾도록 한다.

## 2. 주요 기능

사용자 쿼리를 받아 관련 사진을 검색하여 제시하는 RAG 기반 챗봇 웹 서비스

## 3. 서비스 구동 예시

**Input 1**: 

- 하루 동안 사용자가 촬영한 사진 이미지들
- 각 사진에 포함된 EXIF 메타데이터
    - 촬영 시간 (timestamp)
    - GPS 좌표 (위도/경도)

**Input 2**: 사용자 쿼리

**Output:** 사용자의 요청에 맞는 사진을 제시

```bash
INPUT = "지난달에 친구랑 갔던 파스타 맛집 사진 찾아줘"

OUTPUT_EXAMPLE = 
"
지난달 합정에서 친구들과 파스타를 먹었던 기록이 있습니다.

[2026-01-12 | 합정동 레스토랑]
- 합정의 레스토랑에서 친구들과 파스타와 와인으로 저녁 식사를 함.
- 관련 사진: p_0202, p_0205, p_0210
"
# 실제로는 사진 ID만 출력하지 않고, 사진 이미지를 반환.
```

## 4. 필요한 데이터셋

학습 데이터: 필요 없음 
(학습 진행하지 않음)

1. **시현용 사용자 데이터**: 팀원들의 실제 사진 갤러리 + EXIF
    - EXIF: 사진의 메타데이터 (날짜, 시간, 촬영)
2. **구글맵 지도 API를 통한 GPS Geocoding 데이터**: 사진의 위치 좌표 메타데이터를 의미있는 장소 관련 정보로 변환
    - Reverse Geocoding API 사용 ([네이버 지도 API](https://api.ncloud-docs.com/docs/ai-naver-mapsreversegeocoding-gc))
    - ex. (latitude, longitude) = (37.5563, 126.9237) → “마포구 연남동”

3. **RAM++ (Recognize Anything Plus Plus)**: 사진 데이터에서 사물/행동/장소 키워드 태그 추출
4. **Moondream 2 (Vision Language Model)**: 사진의 전반적인 분위기와 행동을 묘사하는 자연어 캡션 생성

## 5. 전체 파이프라인

### **Data Ingestion & Processing**

1. 사용자가 촬영한 사진을 서비스에 업로드한다. <TODO>
    - 사진은 GPS 태그가 꼭 포함되어 있어야 한다.
2. 사용자의 사진을 입력으로 받으면, EXIF 메타데이터에서 촬영 시간과 GPS 좌표를 추출한다.
3. GPS 좌표는 Geocoding API (Naver/Google/Nominatim)를 사용하여 Reverse Geocoding을 통해 의미 있는 장소 정보(동/구/POI)로 변환된다.
4. 이벤트 클러스터링
    - **시간 기반 분할**: 이전 사진과 **2시간(120분)** 이상 차이가 나면 새 이벤트로 분리.
    - **거리 기반 분할**: **Anchor(이벤트 시작점)** 기준으로 **500m** 이상 이동 시 무조건 새 이벤트로 분리.
    - **체류(Stay) 판정**: Anchor 반경 **50m** 이내에 머무르는 경우 '체류'로 판단하여, 시간 임계값을 **12시간(720분)**으로 완화 (한 장소에서 오래 머무는 경우 배려).
    
    → 같은 이벤트로 판정
    
    예시:
    12시 정각 홍대입구에서 사진을 찍음 (새 이벤트 생성)
    -> 13시 반 홍대입구에서 200m 떨어진 카페 사진 (같은 이벤트 - 시간/거리 만족)
    -> 15시 홍대입구에서 400m 떨어진 당구장 사진 (같은 이벤트 - 시간은 1.5시간 차이지만 거리 500m 이내)
    -> 16시 홍대입구에서 600m 떨어진 볼링장 사진 (새 이벤트 - 거리 500m 초과)
    
    - 시간 기준은 연쇄적으로 느슨하게, 공간 기준은 다소 타이트하게 잡아서 확실히 같이 한 일들끼리 묶으려는 의도
5. 전처리된 사용자 사진 데이터를 DB에 저장한다.

### **Feature Engineering**

**Image Analysis & Embedding Generation**

1. **RAM++ 태그 추출**:
    - 사진에서 4500여 개의 사전 정의된 태그 중, Confidence Score가 높은 태그를 추출한다.
    - 태그는 의미론적 검색(Semantic Search)의 핵심 키워드로 사용된다.
2. **Moondream 2 캡션 생성**:
    - 사진을 보고 "남자가 식당에서 피자를 먹고 있다"와 같은 자연어 설명을 생성한다.
    - 단순 키워드(태그)로는 알 수 없는 문맥(Context), 분위기, 행동의 인과관계를 설명하여 검색 저항성을 높인다.
3. **통합 임베딩 생성 (e5-base)**:
    - `RAM++ 태그` + `Moondream 캡션` + `장소/시간 메타데이터`를 하나의 텍스트로 결합한다.
    - 이를 `intfloat/multilingual-e5-base` 모델을 통해 768차원 벡터로 변환하여 DB에 저장한다.
    - 검색 시, 사용자의 질문도 같은 모델로 벡터화하여 코사인 유사도로 가장 관련성 높은 사진을 찾는다.

**Semantic Filtering (Legacy - 참고용)**
*(아래 내용은 초기 기획이며, 현재는 e5 임베딩의 시맨틱 검색 성능에 의존하고 있음. 추후 검색 품질 개선 시 참고)*

키워드를 **장소/사물/인물/활동** 카테고리로 분류하여 관리한다.

- **우선순위:** `인물(Person/Friend)` > `활동(Eating/Walking)` > `장소(Cafe/Park)` > `사물(Cup/Chair)`.
- LLM에게 전달할 때 "중요한 태그 순"으로 정렬하여 전달하면 답변의 질이 훨씬 좋아집니다.
1. **Recognize Anything Model ++**을 사용하여 사진 데이터에서 **사물** 키워드를 생성한다. 
2. Reverse Geocoding된 **위치 메타데이터**의 POI를 사용하여 **장소, 활동** 키워드를 생성한다.
3. 각 카테고리의 키워드마다 중요도를 매긴다. 
    1. *Option 1.* 키워드를 LLM에게 주고, 주 키워드만 뽑아달라고 하기
        - **상황:** 숲속에서 캠핑하는 사진
        - **RAM의 출력:** `[나무, 풀, 하늘, 구름, 텐트, 의자, 사람, 불, 연기, 신발, 흙, 초록색, 파란색...]`
            
            → 이거를 LLM한테 맥이면 `신발`이나 `흙` 같은 건 배경 요소(Background noise)로 인식하고 버리고, 캠핑 상황임을 인지할 수 있지 않을까?
            
    2. *Option 2.* TF-IDF로 개수 기반 가중치 지정
        - 전체 사진 데이터의 키워드 중 자주 사용되는 것 (ex. 하늘, 조명, 책상, …)
        - 자주 사용되지 않는 키워드는 중요도 높음
        - 이벤트 클러스터링 필요 (이벤트 내에서 중요도 측정)

키워드 분류 예시

**1. 활동 (Activity)** 

*모델이 포착한 사물과 장소의 조합으로 추론되거나, 특정 동작 태그로 추출되는 키워드*

- **예시:** 식사, 산책, 운동, 업무(미팅), 쇼핑, 드라이브, 캠핑, 여행, 데이트, 휴식, 공연 관람, 카페 투어, 요리, 독서

**2. 장소 (Place)**

*Reverse Geocoding을 통해 얻은 POI 정보와 이미지의 배경(Scene) 분석을 통해 결정되는 키워드*

- **예시:** 카페, 레스토랑, 공원, 사무실, 헬스장, 백화점, 해변, 산, 집(실내), 영화관, 전시장, 학교, 공항, 기차역

**3. 사물 (Object)**

*RAM++와 같은 객체 탐지 모델이 사진 속에서 직접 찾아낼 수 있는 구체적인 물체*

- **예시:** 커피, 케이크, 노트북, 스마트폰, 키보드, 운동화, 아령, 가방, 쇼핑백, 텐트, 모닥불, 와인잔, 책, 꽃다발, 반려동물
- **4. 인물 (Person)** (일단은 사용하지 않음)
    
    *특정 개인을 식별하지 못하더라도, 사진의 분위기나 인원수, 구도를 통해 파악 가능한 키워드*
    
    - **사용 제안:** 인물 식별이 어렵다면 다음과 같은 **'일반 명사'**나 **'상태'** 위주로 구성하는 것이 RAG 검색에 훨씬 유리합니다.
    - **예시:** * **인원 중심:** 혼자(1인), 커플(2인), 단체(다수), 군중(Crowd)
        - **관계/유형(추론):** 친구들, 아이(Child), 아기(Baby), 노인
        - **구도 중심:** 셀카(Selfie), 전신사진, 뒷모습
        
        → 문제: 그러면 이벤트에 참여한 인물 중 일부만 찍히면 어떡하지? (사진 구도상 4명이 놀았는데도 1명만 찍힐 수 있으니까)
        (인물 키워드는 나중에 생각하기)

4. LLM을 이용하여 하나의 이벤트에 속한 사진들에서 사진별 중요도를 매긴다.

## 6. 데이터 활용 및 기술스택

1. **이미지 처리 (CV)**
    - 사진 속 대상 또는 상황에 대한 검색을 하기 위해서는 이미지 처리 필요
        - ex. “내가 친구들과 커피를 언제 마셨지?” → 사진에서 ‘사람’, ‘커피’ 찾음
    - **RAM++ & Moondream** 사용하여 사진에 키워드 태깅 및 캡션 생성
        - 이를 RAG embedding에 사용
        - ex. 사진에 “커피와 케이크가 있는 테이블” 태깅 → “내가 친구들과 커피를 언제 마셨지?” → ‘커피’ 키워드를 통해 사진 찾음
2. **사진 키워드 중요도 선정 (LLM)** <TODO> (구현 안 해도 될수도)
    - **상황:** 숲속에서 캠핑하는 사진
    - **RAM의 출력:** `[나무, 풀, 하늘, 구름, 텐트, 의자, 사람, 불, 연기, 신발, 흙, 초록색, 파란색...]`
        
        → 이거를 LLM한테 맥이면 `신발`이나 `흙` 같은 건 배경 요소(Background noise)로 인식하고 버리고, 캠핑 상황임을 인지할 수 있지 않을까?
        
    - 발생할 수 있는 문제: Hallucination에 의한 중요도 오류
    - *현재 구현: RAM++의 Confidence Score를 중요도로 사용하며, LLM 재정렬은 적용되지 않음.*
3. **DB Retrieval**
    - 일기 정보를 vector embedding해서 ChromaDB에 저장 (현재 **PostgreSQL + pgvector** 사용)
    - Retrieval은 하이브리드 방식으로 수행
        1. 날짜/장소와 같은 메타데이터를 이용한 간단한 1차 필터링 (SQL SELECT) <TODO>
            
            ex. “홍대에서 찍은 사진들 모두 찾아 줘.” → “홍대” 지역 필터링
            
        2. 필터링된 사진들을 대상으로 한 키워드 텍스트 벡터 기반 semantic search
            
            ex. “홍대 카페에서 찍은 사진들 모두 찾아 줘.” → 1차 필터링된 데이터에서 “카페” 장소 키워드 찾기

        Case A (메타데이터만 존재): semantic_keyword가 비어있음 (예: "저번주 사진 보여줘")
        → Vector Search 생략. 단순 SQL SELECT 실행.

        Case B (키워드만 존재): 날짜/장소 없음 (예: "우울한 느낌의 사진 찾아줘")
        → 전체 데이터 대상 Vector Search 실행.

        Case C (둘 다 존재): (예: "부산 바다 사진")
        → Hybrid Search (메타데이터 필터링 + Vector Search) 실행.

        - 이를 통해 SQL의 정확한 필터링과 Vector의 유사도 검색을 동시에 수행.

        - 사용자가 질문을 던지면, 먼저 LLM이 질문 의도를 분석하여 **'명확한 조건(날짜/장소)'**과 **'추상적 키워드(사물/분위기)'**를 추출한다.
        - 추출된 정보의 유무에 따라 가장 효율적인 검색 방식을 자동으로 선택(Routing)한다.
    
        Case A: Metadata Search (단순 필터링) <TODO>

            상황: 사용자가 "언제", "어디서" 찍었는지 명확한 조건만 제시했을 때.

            동작: 무거운 Vector Search를 수행하지 않고, 가벼운 SQL SELECT 문만 실행하여 즉각 반환.

            예시: "저번 주에 찍은 사진 보여줘"
            → WHERE taken_at BETWEEN '2026-02-09' AND '2026-02-15'

        Case B: Semantic Search (순수 벡터 검색)

            상황: 날짜나 장소 없이, 특정 "사물", "행동", "분위기"를 찾을 때.

            동작: 전체 데이터를 대상으로 Cosine Similarity(유사도) 검색을 수행. RAM++가 생성한 태그 및 캡션 임베딩과 비교.

            예시: "캠핑 가서 찍은 감성적인 사진 찾아줘"
            → 전체 사진 중 '캠핑', '감성' 벡터와 가장 가까운 사진 검색.

        Case C: Hybrid Search (메타데이터 필터링 + 벡터 검색) <TODO>

            상황: 명확한 조건과 추상적 묘사가 섞여 있을 때. (가장 흔한 케이스)

            동작:
            1. 1차 필터링 (SQL): 메타데이터(날짜/장소)로 검색 범위를 먼저 대폭 좁힘.
            2. 2차 검색 (Vector): 좁혀진 후보군 안에서만 벡터 유사도 검색 수행.

            예시: "작년 부산 여행에서 먹었던 국밥 사진 찾아줘"
            → 1단계: '부산' + '2025년' 조건으로 10,000장 중 50장 필터링.
            → 2단계: 남은 50장 중에서 '국밥(음식)'과 유사한 사진 최종 발굴.
